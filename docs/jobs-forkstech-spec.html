Technical specification · v0.12 draft

A job pipeline that ends at three.

An agent that polls applicant tracking systems directly, discovers new companies on its own, and narrows roughly twelve hundred daily posting rows down to no more than three worth a focused application.

01What this is for

The problem isn't finding job postings. It's that finding good ones costs an hour a day of attention that should go into the applications themselves.

Job boards optimise for volume and re-listing. A human reading them spends most of their time rejecting: wrong seniority, fake remote, agency repost, already seen last Tuesday. That rejection work is mechanical and legible, which makes it a good candidate for automation. The judgement work — is this company worth a tailored application, and what should the application say — is not, and stays with the human.

So the system does three things: it collects postings from sources that return structured data, it rejects aggressively, and it hands over a short daily queue with enough research attached that writing the application is fast.

Goals

  • Produce a daily queue of zero to three remote product, program, or technical program management roles, ranked, with the canonical corporate application URL for each. Empty is a valid answer.
  • Attach a gap analysis to every queued role: what the posting asks for that the current résumé doesn't surface.
  • Attach a company research payload so the application can open with something specific rather than generic.
  • Grow its own company registry over time, so coverage compounds instead of resetting each run.
  • Track application outcomes, so the scoring can eventually be calibrated against what actually converted.

Non-goals

  • No automated submission. The system prepares; the human applies. Several ATS platforms detect programmatic submission, and templated applications lose the only real edge at this end of the market.
  • No LinkedIn or Indeed. Deliberately out of scope, both as sources and as destinations.
  • No automated résumé generation in v1. V1 imports, validates, and versions the existing portfolio PDF as the active base résumé. Product, program, and technical variants remain reviewed candidate artifacts; generating or rewriting them automatically is deferred.
  • No public listings. This is a single-user tool, not a job board.
  • No email or outreach automation. Warm outreach stays manual and human. This governs contact with companies — a daily self-notification of the frozen queue is in scope.

02The funnel

Every stage exists to make the next stage cheaper. Reject with regex before rejecting with a model.

Fetched~1,200
New / changed~20–80
Hard filters~5–25
Triage~3–20
Deep scored0–20
Queued0–3

Steady-state design hypothesis for roughly 400 active companies. The first backfill is a different workload, and a single consultancy Workday tenant can add hundreds of fetched rows and minutes of polite fetch time — a postings_seen jump after seeding is expected, not a bug. Real counts replace these estimates after two weeks.

Three cost boundaries matter. An unchanged posting stops after its hash is checked, nothing new reaches a model until deterministic filters have run, and nothing reaches the strong model until the fast one has voted. The deep-scoring stage sees at most twenty postings a day, which is small enough to spend real tokens on — full posting text, a versioned résumé, cited company research, and a structured rubric.

Design note

The queue is capped at three even when more score well, and zero is a valid result. The constraint is deliberate: opportunity quality and application quality matter more than throughput. A backlog of forty "good" roles is functionally the same as no queue at all. Overflow stays ranked in the pool; an unreviewed queued role may carry forward for at most three days, then expires rather than repeating forever.

03Architecture

One FastAPI service, one Postgres, one idempotent daily workflow. No queue broker until there's a reason for one.

┌─ scheduler trigger (03:00) ─────────────────────────────────┐
│  acquire Postgres advisory lock                              │
│  create pipeline_run                                         │
│  discovery → ingest → reconcile → filter → triage → deep     │
│                                      → freeze daily_digest    │
│  persist every completed step; release lock                  │
└───────────────────────────────────────────────────────────────┘

      │                    │
  sources/            pipeline/
   ├ ats/               ├ dedupe.py      exact hash + pgvector
   │  ├ greenhouse.py   ├ filters.py     deterministic rules
   │  ├ lever.py        ├ triage.py      configurable fast model
   │  ├ ashby.py        ├ deep.py        configurable strong model
   │  ├ workday.py      └ research.py    cited company enrichment
   │  ├ workable.py        workflow/     step orchestration
   │  ├ smartrecruiters.py
   │  └ recruitee.py
   ├ feeds/            api/              FastAPI routers
   │  ├ wwr_rss.py     web/              Jinja2 + HTMX
   │  └ remoteok.py
   └ scrape/
      └ scrapling_source.py   fallback tier only

  Postgres 16 + pgvector  ·  Docker Compose  ·  isolated jobs_ingress

The trigger may run in-process because the workload is one daily workflow on a single-user system, but correctness does not depend on the clock. The daily trigger is 03:00 in America/Anchorage, deliberately outside Alaska's daylight-saving gap, and digest_on dates are defined in the same zone so "today" never wobbles across server timezone or DST changes. A lightweight hourly reconciliation after 03:00 checks whether today's digest exists and starts one catch-up run when it does not. A pipeline_run records step state, every step is safe to retry, and a Postgres advisory lock prevents the scheduled trigger, reconciliation, startup catch-up, or a manual request from running the workflow twice. If ingest ever outgrows a single process, the natural split is a worker container claiming pipeline_run steps, not a broker.

Prior-art strategy

Start with a clean repository and schema. Port proven pieces from Far Reach Jobs — the Workday adapter, robots handling, Scrapling wrapper, deployment and backup patterns, and relevant tests — but do not inherit its MySQL migrations, authentication utilities, public-user flows, Alaska-specific data model, or generic-source administration. Authentication belongs to the existing Authelia boundary, not this application. This is selective reuse, not a wholesale fork.

A company can have many historical endpoints; an endpoint can fail or retire without erasing the company. A posting version preserves the exact body and raw vendor payload used by a score, and a candidate-profile version preserves the exact location used for state-eligibility judgement. Unactioned, closed postings are eligible for retention cleanup, but anything queued, skipped, or applied remains available for audit.

At startup, CANDIDATE_CITY, CANDIDATE_REGION, and CANDIDATE_COUNTRY are normalized and upserted by content hash; a changed location creates a new active candidate_profile_version instead of mutating the old one. Activation is one transaction that deactivates the prior row before inserting or activating its replacement. The partial unique indexes make single-active a constraint rather than a convention — one active profile, one active résumé per variant. Filter and triage scores may omit those foreign keys, but every deep score requires both and includes them in input_hash.

Candidate résumé source

The canonical public candidate reference is michaelbuckingham.org. Its current résumé is published as a PDF at michael-buckingham-resume.pdf and is the source of truth for the active base résumé in v1. The portfolio HTML is a reference link, not an unversioned model input; project or biography content enters scoring only if it is deliberately imported into a versioned candidate artifact.

At bootstrap and before each scheduled run, résumé sync performs a bounded conditional HTTPS fetch using the stored ETag and Last-Modified values, requires a successful PDF response no larger than 10 MB, hashes the raw bytes with SHA-256, extracts and normalizes the text to Markdown, and rejects empty or obviously incomplete extraction. The first valid import may activate automatically when no active base résumé exists. A later normalized-text change creates an inactive resume_version and sends a self-notification; manual review and activation are required before it affects scoring. A byte-only change with identical normalized text is logged but does not create a new scoring version. Activation deactivates the previous base version in the same transaction, and historical scores continue to reference the exact extracted content they used. Product, program, and technical variants remain manual or n8n-derived versions linked through parent_resume_version_id rather than being silently regenerated from a changed PDF.

Why keep rejections

Filter-stage rejections write a score row with every matching reason and the exact ruleset_version. Without them there's no way to answer "why did I never see any Stripe roles" three weeks later, and no way to tell a broken filter from a quiet market. Counts alone are not enough: the weekly audit draws up to five postings that failed exactly one rule from each rule stratum, plus five uniformly selected postings that failed multiple rules. The multi-rule stratum prevents correlated filters from creating an invisible blind spot.

05Source layer

Prefer documented public career-site interfaces. Treat every undocumented endpoint as an adapter hypothesis with fixtures and health checks.

Most small and mid-size companies embed an ATS rather than building a careers platform. Several ATS vendors expose unauthenticated posting APIs specifically to power those public pages; others expose public Markdown or HTML, and some require tenant-specific calls. The adapter must preserve both the posting page and the final application URL rather than assuming they are the same.

Every adapter implements token_patterns() so discovery harvesters can recognise board URLs without knowing platform details. Recorded response fixtures cover normal, empty, paginated, malformed, and rate-limited payloads. A fetch marked incomplete may update rows it saw, but it may never close rows it did not see.

Fallback tier

Otta, Built In, and Wellfound have no stable public feed and may sit behind bot protection. A Scrapling Spider may use a stealthy session only where robots permits it, with robots_txt_obey=True, a real download_delay, and a descriptive user agent. Adaptive matching must be configured deliberately: enable adaptive parsing, save known-good elements with auto_save=True, then use adaptive=True only as a recovery path. This tier discovers company names and outbound board links; it is not trusted for canonical application URLs.

Failure mode to instrument

The dangerous failure isn't an exception — it's a source that returns 200 OK and zero rows after a redesign. Every endpoint writes a source_fetch row. A source that averaged more than twenty postings and returns zero twice consecutively is marked failing and alerted; neither run is allowed to close its existing postings.

Fetching is tractable. The compounding problem is resolving durable companies to the endpoints that currently publish their jobs.

Other harvesters

  • Remote feeds. We Work Remotely category RSS and Remote OK's JSON endpoint. Used to extract company names and outbound board links, then resolved to ATS tokens.
  • Seed list. Hand-curated, version-controlled. Consultancies and enterprise targets that match prior delivery experience — Slalom, West Monroe, Thoughtworks, Nortal, and similar — most of which sit on Workday or SmartRecruiters.
  • Token resolution. Follow the company's own careers link and inspect recognised board URLs first. Only then try a small set of obvious slugs against each ATS. Cache every attempt so failed guesses are not repeated.
  • Manual add. A form field in the dashboard. Paste any board URL, the system infers platform and token.

Registry hygiene

Companies migrate between ATS platforms, which shows up as an endpoint that used to return postings and now returns 404. After three consecutive failures, mark that source_endpoint failing and flag it for re-resolution. A successful replacement becomes a new endpoint linked to the same company; the old one is retired, never overwritten or hard-deleted.

07Deduplication and hard filters

This stage removes most new or changed candidates and costs nothing. It should be pure, synchronous, versioned, and covered by tests.

Deduplication, in order

  1. Identity. (source_endpoint_id, external_id) unique constraint. Handles re-fetches of the same posting.
  2. Content. content_hash over normalised title, locations, and body. An unchanged hash updates last_seen_at only and skips the rest of the pipeline entirely; a changed hash creates a new posting_version.
  3. Semantic candidate. Cosine similarity above the configured threshold against open postings from the same company flags likely reposts. It does not delete automatically: title family and location overlap must also agree before duplicate_of_id is set. Embeddings use voyage-4 with output_dimension=1024; the model, dimension, and threshold are versioned.

Only one embedding model is active at a time, and similarity queries require embedding_model to equal that configured model. A model change is a maintenance operation: generate all replacement vectors into staging first, then update the affected rows and active configuration in one transaction. The HNSW index receives those row updates normally and is rebuilt only when operational evidence calls for it. Mixed-model comparisons are never allowed, and a failed re-embedding leaves the previous model active.

Tuning discipline

Every rule writes its evidence and all matching reject_reasons, not only the first match. The dashboard shows a weekly histogram, and a scheduled review samples rejected roles — stratified, not uniform. It draws up to five single-rule failures per rule, then five uniform multi-rule failures so correlated rules are not invisible. A uniform sample of title_no_match alone is dominated by obviously irrelevant roles and will never surface the borderline miss. A sudden 60% spike is a bug until proven otherwise; a stable histogram is not proof that the filter is correct.

08Scoring

Two model stages, selected by evidence rather than brand tier. The first is a cheap vote; the second is the one that has to be right.

Triage — fast model

Start with the current Haiku-class model, but configure and store its exact provider model ID. One request per surviving posting, submitted with bounded concurrency or the provider's batch API. Input is the title, company one-liner, structured locations, and the first 1,200 characters of the body. Output uses provider-enforced structured JSON and is deliberately tiny.

{ "score": 0-10, "reason": "<12 words" }

Everything scoring 6 or above advances, capped at twenty. If fewer clear the threshold, fewer advance. Never lower the bar to manufacture volume: a thin day may produce an empty queue.

Deep scoring — strong model

Benchmark a Sonnet-class and Opus-class model against the same labelled postings, then use the least expensive model that preserves queue quality. The request contains the exact posting version, exact résumé version, cited company-research version, and exact candidate-profile version. Location is not decoration: "US remote" postings routinely carve out individual states deep in the body — "excluding AK/HI", an "eligible states" list — where a broad deterministic geography rule cannot safely decide. Verifying state eligibility against the versioned candidate location is a mandatory rubric check, and a failure is a red flag, not a footnote. Scoring stays on separate axes because a blended number hides the thing you actually need to know: which dimension is weak.

{
  "verdict": "apply" | "maybe" | "skip",
  "overall": 0-100,

  "domain_fit":    { "score": 0-10, "note": "one sentence" },
  "seniority_fit": { "score": 0-10, "note": "one sentence" },
  "remote_fit":    { "score": 0-10, "note": "one sentence" },
  "company_fit":   { "score": 0-10, "note": "one sentence" },

  "location_eligibility": {
    "status": "eligible" | "ineligible" | "unclear",
    "evidence": "verbatim eligibility or exclusion text, or null"
  },

  "gaps": [
    {
      "requirement": "verbatim from the posting",
      "evidence_in_resume": "none" | "weak" | "strong",
      "suggested_framing": "how existing experience could address it,
                            or null if it genuinely can't"
    }
  ],

  "hooks": [
    "two sentences on why this company specifically,
     grounded in the research payload — no generic enthusiasm"
  ],

  "resume_variant": "product" | "program" | "technical",
  "red_flags": ["e.g. 'remote' contradicted in the body,
                 state carve-out excludes the candidate,
                 or state eligibility remains unclear"]
}
The field that earns its keep

gaps is the highest-value output in the system. A match score tells you whether to apply; the gap list tells you what to rewrite before you do. suggested_framing must be allowed to return null — a model that always finds a way to claim relevant experience is worse than useless. Every quoted requirement is validated as a substring of the posting before the response is stored.

Research payload

Assembled before deep scoring and stored as an immutable company_research version: what the company actually builds, approximate size, funding stage if applicable, and anything notable in the last year. Every time-sensitive fact carries a source URL and retrieval date; current events must come from live sources, not model memory. Refresh no more than monthly, or immediately after a material company change. The mechanism is Anthropic's server-side web search tool, pinned in configuration: web_search_20260318 is the default, web_search_20260209 is the dynamic-filtering compatibility fallback, and web_search_20250305 is the basic-search fallback. These are capability versions rather than labels for model age; the configured model-and-tool pair must pass a smoke request before a run can spend its research budget. Citations arrive with URLs natively while the system stays on one provider. Each company request permits at most three searches, and a pipeline run permits thirty searches across all companies. The application decrements the run-wide budget rather than relying on the provider's per-request max_uses alone. When the budget is exhausted, fresh cached research may be reused; a company without usable research is deferred from deep scoring rather than filled from model memory. Store the exact research model, prompt, server-tool version, token counts, web-search request count, and cost. Cost accounting assumes research, not scoring, dominates spend.

Queue selection

Rank by overall, fill at most three active slots with verdict = apply, and allow no more than two roles from the same company on the same day. Eligibility is gated deterministically, not by the model's verdict: only eligible and unclear statuses qualify. An ineligible, missing, or malformed status never enters the queue even when the verdict says apply; unclear remains eligible with its red flag rendered on the card. Active carryovers consume slots before new recommendations are selected; the combined queue displays carryovers first, then today's items by rank. Freezing makes digest membership, rank, and score references immutable; item state may still move to skipped, applied, expired, or restored. Later runs on the same day update the pool and carryover state but never regenerate the frozen digest. On freeze, a self-notification through the configured ntfy or SMTP transport reports the combined active count and titles, explicitly including zero-role days. Unreviewed recommendations may carry for three days without being cloned into new digests; after that they expire to history. A skipped posting never re-enters without manual restoration — a skip was a human decision. An expired posting becomes eligible again automatically when a material change produces a new posting_version — expiry was only a timeout. Overflow remains ranked in the pool. Scores are never overwritten — model, prompt, rubric, résumé, candidate profile, research, and posting changes all write a new row.

10Dashboard

Three screens. Build a minimal Today and Tracker only after the terminal queue is credible; build Health after coverage starts expanding.

Today

The default view and the reason the system exists. Zero to three cards, ranked, with carryovers visibly distinguished from today's digest. Each shows the role, company one-liner, the four axis scores, the two-sentence hook, cited research, and the gap list rendered as a checklist. Two primary actions: Open application (the canonical apply URL) and Skip (with a required reason, captured for calibration). Marking a role applied creates the application record, links the résumé version, and prevents resurfacing.

Tracker

Every actual application by current status, with an event timeline underneath. Outcomes are not a strict line: a rejection can occur after any stage, a withdrawal is different from a rejection, and ghosted is its own outcome. The history eventually answers whether high-scoring roles convert better than mid-scoring ones without pretending the hiring process is linear. Applications made outside the pipeline — warm outreach, referrals — enter through manual posting entry with origin = manual and act as the control group: without them, whether the pipeline's picks actually convert better is unanswerable.

Health

Pipeline step state, funnel counts per day, rejection reasons as a stacked bar, false-negative audit samples, per-endpoint postings_seen over time, registry growth, research freshness, and failing endpoints. This is the screen that tells you the system is quietly broken before you notice the queue got boring.

Empty state

Some days there will be nothing worth applying to. The Today screen must say so plainly and show what got closest and why it fell short — not display a spinner, an encouraging message, or three mediocre roles padded out to fill the grid.

Access control

This publicly resolvable hostname holds a résumé, an application history, and a strategy. NPM and Authelia form its sole authentication boundary:

  • NPM invokes the existing ForksTech Authelia forward-auth endpoint at /api/verify before proxying every HTML, static, and API path. Authelia gets an explicit jobs.forkstech.com access-control rule for user michael; there are no route bypasses. The application implements no login page, password storage, user table, authentication cookie, or authenticated session.
  • The existing auth.forkstech.com portal remains Tailscale-only. Consequently, a new or expired browser session can authenticate only while the client is on the tailnet and can resolve the portal's documented hosts entry. This Tailscale-required access posture is intentional. The jobs rule uses one_factor, matching the host's current protected-service policy; do not describe it as MFA unless that policy is explicitly changed to two_factor.
  • Authelia owns credentials, authentication cookies, session rotation, and login throttling. The application still protects every state-changing request against CSRF with strict same-origin validation and a form or request token backed by CSRF_SECRET; delegating authentication does not make CSRF disappear.
  • Application rate limits and audit records key on the real client IP. The current Cloudflare record is DNS-only, so NPM overwrites X-Forwarded-For from the direct client address and Uvicorn accepts forwarded headers only from the inspected jobs_ingress CIDR supplied as FORWARDED_ALLOW_IPS. If Cloudflare proxying is enabled later, NPM must instead sanitize and map trusted CF-Connecting-IP to X-Forwarded-For, and the origin firewall must accept public HTTP/S only from Cloudflare. Never trust either header from arbitrary peers. CIDR values in forwarded-allow-ips require Uvicorn 0.31.0 or newer; pin that dependency floor or higher.
  • The application does not use forwarded identity headers for authorization. If an Authelia identity header is displayed or retained for audit purposes, NPM must remove the client-supplied value and overwrite it from the successful auth response.
  • robots.txt disallowing everything, plus X-Robots-Tag: noindex, nofollow on all responses.
  • The initial DNS-only deployment relies on the host's UFW and DOCKER-USER guard to expose only ports 80/443 publicly. Cloudflare proxying plus Cloudflare-only origin ingress or a Tunnel is a later hardening option, not an assumption baked into Phase 1.
  • API keys in the environment only. Never in the image, never in the repo.
  • Résumé text and model prompts are redacted from application logs. Provider request IDs are retained; full requests are not.
  • Backups fold into the existing ForksTech Restic-to-Backblaze workflow: the tracked backup script creates a logical pg_dump of jobs-postgres, and the existing repository backup captures compose configuration. A documented restore test is performed quarterly.

Politeness

A descriptive user agent with a contact address, one request per second per host with jittered backoff, conditional requests where ETag or Last-Modified is offered, and robots_txt_obey=True on every Scrapling Spider. Public career-site endpoints are intended for this kind of read, but nothing about that justifies hammering them.

13Build phases

Each phase ends at something usable. Nothing ships that can't be run end to end.

Phase 1 · vertical slice

Prove the queue

Thirty hand-picked companies, three public ATS adapters, and the full path from fetch to a frozen terminal queue.

  • Precondition: local jobs Git repository at /Users/michaelbuckingham/Documents/my-apps/jobs initialized on main, private GitHub jobs remote created and visibility verified, and this specification committed
  • Company, endpoint, run, posting-version, résumé-version, candidate-profile-version, score, and digest migrations
  • Portfolio PDF bootstrap, text-extraction validation, and versioned base-résumé activation
  • Greenhouse, Lever, and Ashby adapters with recorded fixtures

  • voyage-4 semantic duplicate flagging with manual validation

Harden operations

Add the expensive and failure-prone edges after the structured-source core is stable.

Scope discipline

This is a real project being built during a job search, which creates an obvious failure mode: the tool becomes the work instead of producing the work. Every phase must end with a usable output, and manual outreach continues throughout. Registry size is not progress if queue precision is still unknown; scraping breadth is not progress if three structured adapters already produce enough roles. If Phase 1 drags, cut Ashby — two adapters prove the path just as well.

14Risks and open questions

Known risks

  • Silent source death. Mitigated by per-endpoint volume history, incomplete-fetch semantics, and zero-row alerts.
  • ATS migration. Endpoints fail without warning. Historical source_endpoint rows preserve the old board while a replacement is resolved.
  • Filter over-fitting. Aggressive rules quietly hide good roles. Mitigated by rejection histograms plus per-rule single-failure samples and a separate multi-rule sample.
  • State carve-outs. "US remote" postings that exclude individual states can evade broad deterministic geography rules. The deep rubric's mandatory eligibility check, fed an immutable candidate-profile version, is the backstop.
  • Scoring drift. Model, prompt, rubric, résumé, and research changes alter what "8/10" means. All are versioned and scores are append-only.
  • Résumé source drift. The portfolio PDF can change independently of the application. Conditional fetches, raw and normalized hashes, staged inactive versions, and manual activation prevent a site update or bad extraction from silently changing model inputs.
  • Registry bias. HN skews toward startups and away from the enterprise and consultancy roles that match prior delivery experience. The seed list is the counterweight and needs deliberate maintenance.
  • Research hallucination. Current claims without sources produce persuasive but unusable hooks. Time-sensitive facts require live URLs and retrieval dates.
  • Workflow duplication. Restarts or multiple API processes can trigger the same run. Idempotent steps and a Postgres advisory lock are mandatory.
  • Scheduling gaps. Local wall-clock schedules can skip daylight-saving transitions. The 03:00 Anchorage trigger, hourly missing-digest reconciliation, and advisory lock make the date invariant explicit.
  • Authentication bypass. A missed NPM location or Authelia bypass rule would expose private HTML or API data because the application intentionally has no second authentication layer. Protect and test every path, publish no app port, and require an explicit Authelia domain rule.
  • Container lateral movement. Putting an unauthenticated upstream on the shared npm_network would let a compromised neighboring container bypass NPM and Authelia. jobs-api instead uses the two-member jobs_ingress bridge; membership and negative connectivity from an unrelated container are deployment acceptance checks.
  • Proxy trust error. Trusting client-supplied forwarding headers defeats audit attribution and application throttling. NPM must normalize the client address and Uvicorn must trust only the inspected proxy-network CIDR.
  • Privacy leakage. Résumé text can escape through logs or model-debug payloads. Store only versioned inputs, redact logs, and retain provider request IDs instead of full requests.

Open questions

  • Should the queue adapt to outcomes? Once fifty applications have resolved, scoring could be calibrated against what actually converted — but fifty is a long way off, and premature calibration on ten data points is worse than none.
  • Does the n8n résumé generator produce reviewed variants from the portfolio-seeded base résumé, or get replaced? Either way, every generated variant must retain parent_resume_version_id; running two untracked generation paths is worse than either.
  • Which strong model earns production use? Decide with the labelled set; do not assume the most expensive tier is materially better for this rubric.

Success metrics by horizon

  • Early: precision at three — the share of queued roles that survive human review — plus minutes of attention required per useful role.
  • Safety: desirable-role rate in the weekly rejection sample, segmented by single-rule stratum and multi-rule failures.
  • Later: screen, interview, and offer rates per hundred applications, segmented by score band and résumé version.
  • Never: queue size or registry size by themselves. Both are trivial to increase without improving the search.
Expectations

A perfectly functioning version of this system can still produce a flat funnel for weeks. Cold applications to small companies convert in the low single digits regardless of match quality. The pipeline's job is to make each application cheap enough to write well and specific enough to be worth reading — not to make the market respond faster than it does.
